FeedShop_Backend — 성능 개선 작업 이어하기용 프롬프트 (develop 기준)
================================================================================
이 텍스트를 새 대화에 붙여 넣고, 아래 맥락으로 작업을 이어가면 됩니다.

[저장소·브랜치]
- 경로: FeedShop_Backend (Gradle, Spring Boot 3.3, Java 17)
- 원격: origin = dbp-jack/FeedShop_Backend_Refactoring, upstream = ECommerceCommunity/FeedShop_Backend
- 현재 정책: 성능 개선 전용 브랜치(feature/event-feed-performance)는 삭제하고, develop에서 이어가거나 새 브랜치를 따서 진행
- 로드맵 파일: docs/event-performance-roadmap.md (Phase 1~4 + 포트폴리오 Before/After 캡처 가이드 포함)
- 주의: 위 feature 브랜치를 삭제했기 때문에, Redis/캐시 분기·searchEvents 2-step 등 구현 커밋은 develop 기본 트리에 포함되어 있지 않을 수 있음. 코드가 필요하면 Git reflog / GitHub에서 삭제 직전 브랜치 SHA 복구 또는 아래 로드맵대로 재적용

[이미 해둔 작업 — 과거 feature 브랜치에 있던 내용 요약]
- 이벤트 검색: EventQueryRepositoryImpl 등에서 searchEvents 페이징 + 컬렉션 fetchJoin 충돌을 피하기 위한 2-step 조회(페이징된 ID 조회 후 detail/rewards fetch join) 구조
- Redis: docker-compose에 Redis, application-redis.properties + 프로파일 redis, spring-boot-starter-cache + spring-data-redis 명시
- 캐시: redis 프로파일에서 spring.cache.* 로 Redis 캐시, 그 외 ConcurrentMapCacheManager(CacheConfig). 피드 노출 이벤트 목록 @Cacheable("availableEvents")
- 직렬화: Boot 기본 JDK 직렬화 → EventSummaryDto(및 내부 Reward) Serializable
- @CacheEvict: EventCreate/Update/Delete, EventStatusService(전체·단건 상태 갱신)에서 availableEvents 무효화
- 기타: IDE용 feedshop-*.code-workspace, .vscode 일부, README 일부, perf/k6 스켈레톤 등이 feature에 포함되어 있었음 — develop에는 cherry-pick 등으로 일부만 들어올 수 있으니 파일 존재 여부를 확인할 것

[아직 하지 않았거나 미완인 작업 — 로드맵 순]
- Phase 1-1: 기준선 Before 수치·재현 조건(대상 API, p95, 쿼리 수, k6 등) 문서화
- Phase 1-3: getAllEvents 경로 N+1 완화(fetch join 전용 쿼리, @EntityGraph, batch size 등 확정·적용)
- Phase 1-4: Phase 1 Before/After 1차 정리
- Phase 2A-5: 캐시 miss → DB → 재적재 흐름 점검·After 2차 메모
- Phase 2-B 전체: 투표 Redis INCR/DECR, DB 유니크, SoT·동기화, k6 동시성 스모크 등 (현재 FeedVoteService는 DB+엔티티 카운터 중심)
- Phase 3: Result 문서에 실제 적용분·실측 수치만 반영
- Phase 4: docs/event-performance-troubleshooting.md (코드 변경 없이 트러블슈팅만)

[문제 해결 섹션 — 문서·포폴에 넣을 때 채울 항목]
로드맵 Phase 4(`docs/event-performance-troubleshooting.md` 예정)와 동일한 뼈대로, 이슈마다 아래를 짧게라도 적어 둘 것.
- 증상: 사용자/운영 관점에서 무엇이 이상했는지(느림, 500, 숫자 불일치 등)
- 재현: API·파라미터·동시성·데이터량·프로파일(예: redis 유무)
- 기대 vs 실제: 기대 동작 한 줄, 실제 관측 한 줄
- 원인: 쿼리(fetchJoin+페이징, N+1), 캐시 직렬화/TTL/stale, Redis 연결·타임아웃, 투표 경쟁 등 가설과 근거
- 해결: 적용한 코드·설정 변경 요약(파일/PR 링크)
- 롤백: 되돌리는 방법 한 줄
- 설정 스냅샷: Redis 호스트/포트, spring.cache.*, 캐시 이름(availableEvents), 키 규칙(가명화 가능)
- 함정 메모: 페이징+컬렉션 fetchJoin, JDK 직렬화와 DTO 변경, 캐시 스탬피드, @CacheEvict와 트랜잭션 순서 등

[성능·캐시·투표 동작 확인 — 테스트해야 할 API 목록]
아래는 EventReadController·FeedVoteController 기준 경로다. 인증 필요 API는 JWT 등 실제 토큰으로 호출할 것. 측정 시 page/size·keyword·정렬을 Before/After에서 동일하게 맞출 것.

| 우선순위 | HTTP | 경로 | 인증 | 비고·측정 포인트 |
|----------|------|------|------|------------------|
| P0 | GET | /api/events/feed-available | 공개(설정에 따름) | Phase 2-A 캐시 대상 후보. 연속 2회 호출 시 지연·DB 쿼리 수 비교(캐시 hit/miss) |
| P0 | GET | /api/events/search | 공개 | QueryDSL 검색. page,size,status,type,keyword,sort 조합 고정 후 p95·쿼리 로그 |
| P0 | GET | /api/events/all?page=&size=&sort= | 공개 | Phase 1-3 N+1 완화 대상. 목록 + 연관 로딩 쿼리 수 |
| P1 | GET | /api/events/{eventId} | 공개 | 상세 1건. 참고용 베이스라인 |
| P1 | POST | /api/events (JSON 또는 multipart 생성 엔드포인트) | 인증 | Swagger에서 consumes 구분. 생성 후 GET /feed-available로 캐시 무효화 검증 |
| P1 | PUT | /api/events/{eventId} 및 /api/events/{eventId}/multipart | 인증 | 수정 후 캐시·목록 일관성 |
| P1 | DELETE | /api/events/{eventId} | 인증 | 삭제 후 목록·캐시 |
| P2 | POST | /api/feeds/{feedId}/vote | 인증 | Phase 2-B 전후 동시 투표·숫자 정합. 리워드 부가 로직 있음 |
| P2 | DELETE | /api/feeds/{feedId}/vote | 인증 | 취소 후 카운트 감소 |
| P2 | GET | /api/feeds/{feedId}/vote/count | 공개 | 투표 수 조회. Redis 도입 시 Redis vs DB 순서 검증에 사용 |
| P2 | GET | /api/feeds/events/{eventId}/vote/count | 공개 | 이벤트 단위 투표 합 |
| P2 | GET | /api/feeds/{feedId}/vote/check | 인증 | 투표 여부 |
| P3 | POST | /api/feeds/{feedId}/vote/sync | ADMIN | 관리용 동기화. 부하 테스트 전후 정합성 |
| P3 | POST | /api/feeds/vote/sync-all | ADMIN | 전체 동기화. 운영 주의 |

보조: Swagger UI `/swagger-ui/index.html`에서 동일 API 반복 호출·Timing 캡처. 부하는 `perf/` k6 스크립트가 있으면 해당 시나리오와 맞출 것.
